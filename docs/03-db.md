# 03 — DB

`@bedrock-core/db` — persisted documents: arbitrary JSON, addon-shaped, no UI, stored in the
dynamic properties the target itself can hold. Config is a collection on it with a form on top
([05-config](./05-config.md)). Measured before it was designed: a DP write is 17 µs, a DP string
caps at 32 767 characters and throws, a block entity holds ~950 bytes
([S2](./spikes/S2-dynamic-property-costs.md), [S4](./spikes/S4-block-documents.md)).

**Decided.** Batching alone would never have justified a subsystem. What does: documents on native
block properties with their lifecycle, validity gates on every target, one host resolver every
scope shares, and lazy per-document migrations. Write-through by default; coalescing is opt-in.

## Shape — *Decided*

```ts
const balances = core.db.collection('balances', { schema: schema<{ gold: number; lastSeen: number }>() });

balances.for(player).get();                     // sync, in-memory, defaults filled
balances.for(player).patch({ gold: 10 });       // written through, 17 us; merges deep
balances.for(player).subscribe(cb);             // local change events, an observable, like every config leaf
```

- **No declared location.** A collection does not say *where* it stores; it stores in whatever the
  target itself can hold, resolved at the call — see
  [Where a document can live](#where-a-document-can-live--capability-not-declaration).
- **Write-through by default.** A write updates the in-memory document and the DP in the same
  call — 17 µs, nothing to flush, nothing to lose. `coalesce: true` per collection turns on
  write-behind (dirty set, one flush per tick) for the counter that is bumped a hundred times a
  tick; it is the exception, and it carries the vanishing-target rules below.
- **`patch` merges deep.** A nested object merges key by key, an array replaces the one there,
  `undefined` deletes a key. What is stored is what was written; `defaults` are filled in on the
  way out, at every depth, so a key nobody wrote keeps following its default. A collection's
  `normalize` runs over every write — its own and a peer's RPC — before the bytes are stored.
- **Chunked at 32 767 characters.** The engine throws past that (measured), so a world-located
  document above it is split into `key#0..n` plus an index entry; transparent on read. Documents
  are discouraged from getting there — it is a safety net, not a design.
- **Lifecycle is derived from the resolved host**, not declared: entity documents load on first
  `for()` or on load with a subscriber and unload on remove; block documents are lazy with
  `forget()` explicit; world documents load at boot.
- **A document schema and migrations from day one** — see
  [Document schema](#document-schema-and-migrations--core-not-optional). Persistence without a
  declared version is a trap: the shape on disk outlives the code that wrote it. **No UI**,
  though: a document is not a settings form.
- **Cross-addon access is a query**, never this API:
  `core.query.observe(peerDoc<Balance>(ns, 'balances', id))` — a cache with a status ([04-query](./04-query.md)).
  Declaring the collection `shared: true` keeps those caches warm through the mirror.

Hot-path cost when unused: zero — no collection, no flush loop registered. Measured in the
engine ([S8](./spikes/S8-db-in-game.md)): `for(player).get()` 14 µs, write-through `patch` 28 µs
against a 12 µs raw property write, coalesced `patch` 6 µs, a block document 91 µs to create and
56 µs to visit through `all()`. The engine is QuickJS: hosts, handles and stores are classes, a
handle resolves its target once per tick, and the index is written behind.

## Document schema and migrations — core, not optional

Config's schema exists to be *drawn*: labels, ranges, scalars, a form. A document schema exists to
be *trusted*: it says what the bytes on disk are supposed to be, so a document written by version 1
of an addon is still readable by version 4. Those are different jobs, so this is a different
declaration with no display fields at all.

```ts
const elevators = core.db.collection('elevators', {
  accept: blockTypes('papi:elevator'),

  schema: schema<ElevatorDoc>({
    version: 3,
    defaults: { configured: false, facing: 'north', particles: true },
    migrate: {
      2: doc => ({ ...doc, facing: doc.facingDirection ?? 'north' }),   // renamed
      3: doc => { const { legacyMode, ...rest } = doc; return rest; },  // dropped
    },
  }),
});
```

The document type is named once, in `schema<T>()`, never as a type argument on `collection`:
TypeScript infers all of a call's type arguments or none, and the acceptor and `require` have to be
inferred for the static check below to run.

Rules, all of them shared with config's mechanism ([01 §2](./05-config.md#2-schema-migrations--decided))
so there is one concept to learn:

- **`version` defaults to `1`** and a collection that never declares it never migrates — zero cost,
  and declaring a version for the first time is itself the upgrade path.
- **Every document carries its own `v`.** Config migrates a whole target on load; db migrates
  **one document, lazily, on first read**, because block and entity documents are never all loaded
  at once. A world that has 4 000 elevators pays for the ones someone actually touches.
- **`migrate` steps are `doc → doc`, untyped in and untyped out.** The old shape no longer exists
  in the source, so the framework cannot type it and does not pretend to; a creator who wants
  safety keeps the old type around and annotates the step. What is guaranteed is the *result*:
  after the last step, `defaults` fill missing keys and the document is handed over.
- **`defaults` are not persisted.** Only what an addon actually wrote is stored, so changing a
  default reaches every existing document with no migration — same as config, whose `normalize`
  additionally drops a written value that equals its default.
- **`normalize` is the write-time pass.** `doc → doc`, run on `set`, `patch` and a peer's RPC
  alike, over the document about to be stored. Coercion, clamping, dropping what should not be
  stored — the place for anything that must hold whoever writes.
- **A document that cannot be parsed or migrated is quarantined, not deleted**: moved aside under
  the same key with a `#bad` suffix, `undefined` returned, one log line naming the collection and
  the target. Persistence that silently discards a player's data on a bad deploy is worse than an
  error, and the quarantined copy is what makes a fix possible.

A typed schema *builder* (declare the shape, get validation and the TS type from one source) is the
obvious next step and layers on top without changing any of the above. It is not in the first cut
because `defaults` plus the caller's own TS type already covers the failure that matters.

## Where a document can live — capability, not declaration

`location: 'entity' | 'block' | ...` is the wrong knob. The platform decides which objects hold
dynamic properties; enumerating them in our API means re-releasing every time Mojang adds one, and
it makes every collection declare a fact the target already knows about itself. So: **db
accepts any target that can hold bytes, decided by a cheap cached probe, and a collection states
its requirements as rules rather than a place.**

### The probe

```ts
core.db.where(target);
// -> { ok: true,  host: 'own',     budget: 950,   enumerable: false, ... }
// -> { ok: true,  host: 'proxied', budget: 32767, enumerable: true,  ... }
// -> { ok: false, reason: 'detached-copy' }
```

`resolveHost(target)` in order:

1. **Explicit refusals first.** `ItemStack` is the trap this design exists to catch, measured
   both ways in [S5](./spikes/S5-abi-survey.md): a *stackable* item has the full DP API and
   **throws** on write (`Cannot set dynamic properties on stackable items`); a *non-stackable* one
   accepts the write on a detached copy and a fresh read gives `undefined`. A structural test alone
   accepts both. Refused by name, with `ContainerSlot` named in the error.
2. **Direct ABI** — `'setDynamicProperty' in target`: world, entity, player, `ContainerSlot`, and
   anything Mojang adds later. Nothing is hard-coded.
3. **Component ABI** — `target.getComponent('minecraft:dynamic_properties')`: a block whose type
   declares `minecraft:block_entity`. (`minecraft:block_actor_dynamic_properties` is present on
   *every* block item, stackable stone included, so its presence proves nothing — the direct ABI is
   checked first and wins.)
4. **Proxied fallback** — the target holds nothing of its own, so the document lives in a world DP
   keyed by the target's identity. `Dimension` is here **permanently**: it has no DP methods at all
   (verified), and so is any vanilla block type, whose JSON is not ours to extend.

### The catch: two ABIs, not one

There is no single interface to type against. Measured shapes:

| Family | Methods |
| --- | --- |
| `World`, `Entity`, `Player`, `ItemStack`, `ContainerSlot` | `getDynamicProperty` / `setDynamicProperty` / `setDynamicProperties` / `getDynamicPropertyIds` / `getDynamicPropertyTotalByteCount` / `clearDynamicProperties` |
| `BlockDynamicPropertiesComponent`, `ItemBlockDynamicPropertiesComponent` | `get` / `set` / `totalByteCount` — no enumeration, no clear |

So `DpHost` is our own three-method interface (`read` / `write` / `bytes`, plus optional `keys`)
and the resolver returns a ~20-line adapter over whichever family answered. That adapter is the
whole cost of the idea, and it is also where the missing `keys` on the component family becomes
the `enumerable: false` capability below.

### Cheap means cached by type, not by instance

A probe is one `in` check or one `getComponent` — but `getComponent` at ~10 us on a hot path is not
free, and it does not have to run twice: **whether a type holds its own properties is a property of
the type.** `minecraft:block_entity` cannot appear in permutations (documented), so every block of
a type answers identically; likewise every entity of a type, every container slot, the one world.

So the cache key is `typeId` for blocks and entities, a constant for world and slots. First call
per type: one probe. Every call after: one `Map.get` — the same cost as switching on a declared
`location` string, which is why this is not a performance trade.

One rule: **never cache a failure.** `getComponent` on a block in an unloaded chunk throws
`LocationInUnloadedChunkError`, and caching that as "this type holds nothing" would silently demote
a whole block type to the proxy for the rest of the session. A throw means *unknown* — re-probe.

### Capabilities, and the rules over them

The probe yields a capability record, and a collection declares what it needs:

| Capability | Meaning | `own` | `proxied` |
| --- | --- | --- | --- |
| `own` | the bytes die with the target | yes | no — needs cleanup and an index |
| `enumerable` | keys can be listed, so `all()` needs no index | entity/world/slot: yes; block: **no** | yes |
| `budget` | bytes before a throw | ~950 per block entity; 32 767 chars per value on world / entity / slot | 32 767 per DP value |
| `readableWhenUnloaded` | reachable with the target not loaded | no | yes |
| `batch` | `setDynamicProperties` for a one-call flush | direct family only | yes |

```ts
core.db.collection('elevators', {
  schema: schema<ElevatorSettings>(),
  accept: accepting<Block>(typeId => typeId.startsWith('papi:')),   // optional; omitted means anything storable
  require: { own: true },                                            // refuse rather than silently proxy
});
```

`accept` is the cheap condition over the target's **type id** — never the instance, so the answer
can be asked once per type and cached with the probe. `require` is the
honest half: an addon that wants "data dies with the block, no orphans, no index" says `own: true`
and gets a refusal with a reason on a vanilla block, instead of a silent fallback to world DPs and
a cleanup problem it never asked for. Omit it and the proxy is used — the right default for an
addon that just wants storage.

This is the shape `core.features.add()` already has — declare a condition, the framework enables
what satisfies it — so the pattern is not new to the runtime.

### Config

Config's three scopes are three collections — `config-server` accepts the world, `config-dimension`
dimensions, `config-player` players — and the resolver answers where each stores: the world and a
player hold their own, a dimension is proxied onto the world. Config keeps its scope *names*
because a schema is declared against a scope and a UI draws them; a scope names a target kind and
nothing else ([05-config](./05-config.md)).

## Block documents — the case that decides the shape

The concrete ask (PAPI, elevators): per-block settings on world dynamic properties because
blocks have none of their own, and no event for a block vanishing by command, `setBlock`, fluid
or explosion — so deleted blocks leave data behind forever. Today it is one JSON string holding
every block's settings: one DP, one array, parse + filter + stringify on every delete.

```ts
interface ElevatorsBlockIndividualSettings {
  isConfigured: boolean;
  blockLocation: Vector3;         // the key, stored inside the value
  blockDimension: string;
  facingDirection: string;
  elevatorTickParticles: boolean;
  previousElevatorTickParticles: boolean | undefined;
}
```

What the platform gives, verified against the docs (2026-09-02). We are on 1.26.4x; 1.26.50 is
the next release and ships `@minecraft/server` **2.10.0 stable**, which is where block dynamic
properties land — db is built on them, not around their absence.

| Fact | Status | Consequence |
| --- | --- | --- |
| `minecraft:block_entity { dynamic_properties: true }` gives a block its **own** DPs (`BlockDynamicPropertiesComponent`) | **Measured on the 1.26.50 preview with no experiment: works** ([spikes/S4](./spikes/S4-block-documents.md)). `format_version` 1.26.50; cap is 1 024 bytes per pack per block *including* key + overhead (~950 usable), and it **throws** rather than truncates. Not in permutations; docs warn about RAM (1 000 placed: no measurable tick cost) | data dies with the block whatever removed it — the orphan problem does not exist on this backend. **The primary backend.** |
| `carry_over_block_entity_data` loot function + `ItemBlockDynamicPropertiesComponent` | same release train (2.10.0) | settings survive break → item → place. Elevators keep their facing when moved by hand |
| `BlockCustomComponent.onBreak` | **stable**, 2.4.0 | **Measured**: fires on player break, explosion, `/fill`, `/setblock` in destroy **and replace** mode, and script `setPermutation` — the docs exclude the last two; the engine does not. Inside the hook the block is already air and the document is **unreadable** |
| `onPlace` | stable | the create hook |
| pistons | **Measured**: the block does not move and the piston does not extend | no re-keying problem on the native backend; on world DPs `pistonActivate` lists moved blocks |
| one DP per value | 32 KB per DP, shared world byte budget | one-string-for-all caps at ~200 elevators and rewrites everything per change; one DP per block does not |

### Native first, one API — *Decided for 1.26.50*

```ts
const elevators = core.db.collection('elevators', {
  schema: schema<ElevatorSettings>(),
  accept: blockTypes('papi:elevator'),     // which block types may carry a document
  require: { own: true },                  // this collection wants no orphan cleanup at all
});

elevators.for(block).get();                 // undefined until set; validated on read
elevators.for(block).patch({ facingDirection: 'north' });
elevators.for(block).delete();
elevators.all(budget);                      // iterate known blocks, N per tick
```

| Host | Where the document lives | Resolved when |
| --- | --- | --- |
| `own` (component ABI) — **the default** | the block's own DPs (one key, JSON, ≤ ~950 bytes) | the probe finds `minecraft:dynamic_properties` on that block type. The build adds `minecraft:block_entity { dynamic_properties: true }` to every accepted **custom** block's JSON and requires the pack's `@minecraft/server` ≥ 2.10.0 |
| `proxied` | `core-store:b:<addon>:<collection>:<dimId>:<x,y,z>` on the world | the probe finds nothing: **vanilla** block types (their JSON is not ours) and multi-blocks (`minecraft:multi_block` forbids `block_entity`) |

Nobody declares which: the probe answers per block type and the addon never branches. Pre-2.10.0
proxied data from an addon that upgrades migrates on first read — world DP found, block DP absent
→ copy, delete the world key — and that same path is the `proxied` → `own` upgrade for any block
type that later gains an entity.

### Lifecycle — how deletion stops being the addon's problem

On the native backend the **document** needs no lifecycle at all — it is part of the block.
What still needs one is the **index** (which blocks exist, for `all()`), and the `worldKeyed`
fallback needs both.

1. **Db owns one custom component**, `blockCleanup(db)`, that the addon registers once in
   `startup` under its own id and lists in the `components` of every accepted custom block type
   (vanilla types get the validate-on-read fallback below). It has only `onBreak`: drop the index
   entry, and on a proxied host delete the document too. Covers break, explosion, and every
   command mode — for free, for every block collection. A block type that lists a component nobody
   registered is removed from the world, so the registration is not optional.
2. **Validate on read.** `for(block).get()` checks `block.typeId` against `blockTypes`; a
   mismatch means the block was replaced by a means with no event. Native: there is no document
   to clean (it went with the block) — the index entry is dropped. `worldKeyed`: the document is
   deleted too. Every access self-heals.
3. **Index.** World DPs per collection holding the key set (compact: `dim:x,y,z` joined),
   **chunked** — a DP string caps at 32 767 chars and throws past it, so ~1 300 keys per chunk —
   maintained by first `set` and by `onBreak`, which must key by **location** (the document is
   gone by the time the hook runs); validated lazily as (2) walks it. Measured: 1 000 keys =
   24 KB, `getBlock` walk 8 ms. An orphan entry costs ~24 bytes until the next `all()` drops it.
4. **Never enumerate DPs at boot.** The index replaces `getDynamicPropertyIds()` scans entirely.
5. **Explicit `forget(block)`** for addons that replace blocks themselves, and an on-demand
   `sweep(budget)` that walks the index checking types — for operators after a `/fill`.

Residue: on `worldKeyed` only, a replace-mode `/setblock` / `/fill` leaves the document until
the next read or sweep. On the native backend nothing is ever left behind — that is the reason
it is the default.

### Document rules

- **Versioned, lazily.** Each document carries `v`; the collection declares `version` and
  `migrate` exactly as config does ([01 §2](./05-config.md#2-schema-migrations--decided)),
  run when a document is *read*, since block documents are never all loaded. PAPI's
  `configVersion` + `initialized` is this, per document instead of per world.
- **Location is the key, not the value.** `blockLocation` and `blockDimension` disappear from
  the document; `for(block)` supplies them.
- **~950 bytes is the budget on the native backend** (1 024 including key and overhead; the
  engine throws `World metadata storage limit exceeded`, never truncates). Db checks the
  serialized size before writing and refuses with the collection named, so the failure is ours
  and readable, not the engine's.
- **The global-vs-local override pattern** (`elevatorTickParticles` masked by a server setting,
  `previousElevatorTickParticles` remembering the local value) is the config resolution rule —
  stored override → default — with the server value as the default. It belongs in a block-scope
  *config*, not db, once [01 §4](./05-config.md#3-entity-and-block-scopes--on-hold)
  comes off hold; db carries the free-form rest.

### Measure — S4 — **answered 2026-09-03**, see [spikes/S4](./spikes/S4-block-documents.md)

1. Graduation check: does `minecraft:block_entity` work without the experiment on 1.26.50, and
   at which `format_version`? Is the 1 KB limit per pack (1.26.40 wording) what ships?
2. Native backend: does the document vanish on replace-mode `/setblock`? (Expected: yes — good.)
   A piston push? (Expected: block does not move.) Survives world reload and a pack update?
3. Cost: `get` / `set` on `BlockDynamicPropertiesComponent` vs a world DP, per call; RAM per
   block entity at 1 000 placed blocks (the docs warn "use sparingly") — the number that sets
   the documented cap.
4. `onBreak` coverage matrix (for the index and the `worldKeyed` fallback): player, TNT,
   `/setblock … destroy`, `/setblock … replace`, `/fill`, script `setPermutation`, fluid, piston.
5. Index DP size and `all(budget)` walk time at 1 000 and 5 000 blocks.

## Validity — targets that stop existing

Every handle db is given describes a moment, not a thing: a `Block` object goes stale
when its chunk unloads, an `Entity` after removal or unload, an `ItemStack` is a **copy** the
instant it is read. Db must never trust a handle past the call it arrived in.

### The rule: key by identity, resolve per operation

`for(target)` extracts an **identity** and keeps nothing else:

| Target | Identity kept | Re-resolved on every op by | Gate |
| --- | --- | --- | --- |
| block | `dimId` + `x,y,z` | `dimension.getBlock(loc)` | `block !== undefined && block.isValid` and the collection's `accept` still holds for `typeId` |
| entity / player | `entity.id` | `world.getEntity(id)` | `entity?.isValid` |
| item | the `ContainerSlot`, never the `ItemStack` | the slot itself | `slot.isValid && slot.hasItem() && slot.getItem().maxAmount === 1` | 
| dimension / world | id / none | — | always |

So an accessor obtained before a chunk unload or a player rejoin keeps working — the same
guarantee config's `for(entity)` tree already gives — and a stale `Block` the caller holds is
never dereferenced by us.

Items are the odd one: a document on an item lives in the item's own DPs, and an `ItemStack` is
detached — writing to it changes nothing in the world. Db therefore takes a
`ContainerSlot` (live, has `isValid` and DP methods) and refuses an `ItemStack` at the type level. TODO why not item stack? check further

### What each op does when the gate fails

| | Read | Write | Delete |
| --- | --- | --- | --- |
| target gone (entity removed, block replaced by another type, slot empty) | `undefined`; on the `worldKeyed` block backend the document is also deleted — this is the validate-on-read cleanup | throws `StoreTargetError` naming collection + id — writing to nothing is a bug at the call site | no-op, index entry dropped |
| target merely unloaded (chunk not loaded, entity not ticking) | `worldKeyed` block docs still read — world DPs need no chunk; everything else `undefined` | `worldKeyed`: writes go through; native block / entity / item: throws | as write |

`for(target).available` exposes the gate result for callers that want to branch instead of
catch. A read returning `undefined` is deliberately ambiguous ("no document" vs "cannot know");
`available` is how to tell.

### Write-behind meets a vanishing target

Coalescing writes into one flush per tick opened a window: dirty at tick N, target gone before
the flush at N+1. `system.run` cannot flush at the *end* of the same tick — nothing can. So
the write mode follows the location:

| Host | Write mode | Why |
| --- | --- | --- |
| `proxied` (world, dimension, vanilla block) | write-through; `coalesce` allowed | the world cannot vanish, so coalescing here is safe — it is just rarely worth it (17 µs a write) |
| `own`, target not entity-shaped (block, item slot) | write-through only | the target can be gone next tick. A block write is 11 µs; a **slot write is 327 µs** ([S5](./spikes/S5-abi-survey.md)) — slot documents are not for per-tick counters |
| `own` on an entity or player | write-through; `coalesce` allowed with the parking rule | a player leaving in the window loses nothing — db flushes in `beforeEvents.playerLeave` (measured: allowed); an entity unloading is parked and flushed on `entityLoad` |

The rule falls out of the capability record rather than a location name: `coalesce` is offered where
the host is `readableWhenUnloaded` or the target has a load event to flush on, and refused where a
dirty document could die with its target inside the one-tick window.

In `coalesce` mode a flush that finds the entity invalid **parks** the document keyed by id with
a TTL, and writes it on the next `entityLoad` for that id; past the TTL it is dropped with a log
line. Measured: `entityRemove` fires on chunk unload as well as death (indistinguishable), and
the entity returns through `entityLoad` — parking is the right shape. **Players need no park**:
`world.setDynamicProperty` inside `beforeEvents.playerLeave` is permitted and persists, so the
store flushes a leaving player's pending documents there.

### Config scopes get the same gate

`config.player.for(player)` is a tree over `collection.for(player)`, so a write to a player who
left throws the same `DbTargetError` any document does ([05-config](./05-config.md)).

## Keeping peers warm — `shared`

A collection is never mirrored wholesale into other realms: that multiplies memory by the number of
addons and turns every balance change into a broadcast. What a collection can do is publish, under
`core-db/<ns>/<collection>/<key>` on the shared mirror ([02-shared](./02-shared.md)):

- **by default, a version stamp** on every write — every peer query for that key goes stale the
  same tick and refetches on its next read ([04-query](./04-query.md#refetch-triggers--the-minecraft-set));
- **with `shared: true`, the document itself**, and with `shared: { as: doc => summary }` a
  derived subset — peers' queries resolve warm, no RPC, and owner writes arrive as mirror deltas.

```ts
core.db.collection('elevators', {
  schema: schema<ElevatorDoc>(),
  accept: blockTypes('papi:elevator'),
  shared: { as: doc => doc.configured },      // one boolean per elevator, everywhere, this tick
});
```

The cap on what may be `shared` is S6's number. Peers read it through `core.query`, never
`core.shared`: that is what gives them status, staleness, typing and a refused write. **The mirror
never writes back into a document** — a peer that wants a change calls `mutate`, which is an RPC
to the owner.

## Making the compiler check the rules

`accept` and `require` can contradict each other, and most of the time the target *type* already
settles it. Where it does, that is a compile error rather than a runtime surprise.

### `accept` carries the target type

An acceptor is branded with what it accepts, so the collection is generic in its target and
`for()` only takes the matching thing:

```ts
const elevators = core.db.collection('elevators', {
  schema: schema<ElevatorDoc>(),
  accept: blockTypes('papi:elevator'),        // Acceptor<Block>
});
// elevators: Collection<ElevatorDoc, Block>

elevators.for(block);    // ok
elevators.for(player);   // Argument of type 'Player' is not assignable to parameter of type 'Block'
```

Built-in acceptors: `blockTypes(...ids)`, `entityTypes(...ids)`, `players()`, `slots()`,
`worldTarget()`, `dimensions()`, and `accepting<T>(t => boolean)` as the escape hatch. Each returns
`Acceptor<T>`; omitting `accept` gives `Collection<Doc, StorableTarget>` and accepts anything the
resolver can host.

### `require` is checked against what the type can possibly do

Each target type has a statically known capability record. `true` means always, `false` means
never, `boolean` means *the instance decides* and only the resolver can answer:

| Target type | `own` | `enumerable` | `readableWhenUnloaded` |
| --- | --- | --- | --- |
| `World` | `true` | `true` | `true` |
| `Entity`, `Player` | `true` | `true` | `false` |
| `ContainerSlot` | `boolean` — only a non-stackable item holds properties | `true` | `false` |
| `Block` | `boolean` | `boolean` | `boolean` |
| `Dimension` | `false` | `true` | `true` |
| `ItemStack` | — never storable — | | |

One rule covers every conflict: **requiring `true` where the type is statically `false` is a type
error; requiring it where the type is `boolean` compiles and may be refused at runtime with a
reason.**

```ts
core.db.collection('regions', {
  schema: schema<Doc>(),
  accept: dimensions(),
  require: { own: true },
});
// Property '"require.own is impossible: this target type never has it"'
//   is missing in type '{ schema: …; accept: Acceptor<Dimension>; require: { own: true } }'
```

The error text *is* the property name the checker asks for, so the reason shows up in the IDE
without opening this page. Sketch:

```ts
type Caps<T> =
  T extends ItemStack ? never
    : T extends Dimension ? { own: false; enumerable: true; readableWhenUnloaded: true }
      : T extends Block ? { own: boolean; enumerable: boolean; readableWhenUnloaded: boolean }
        : T extends World ? { own: true; enumerable: true; readableWhenUnloaded: true }
          : T extends ContainerSlot ? { own: boolean; enumerable: true; readableWhenUnloaded: false }
          : T extends Entity ? { own: true; enumerable: true; readableWhenUnloaded: false }
            : { own: false; enumerable: true; readableWhenUnloaded: true };

type Conflicts<T, R> =
  | (Caps<T> extends never ? 'accept: an ItemStack is a detached copy — use slots() instead' : never)
  | { [K in keyof R & keyof Caps<T>]: R[K] extends true ? (Caps<T>[K] extends false ? `require.${K & string} is impossible for this target type` : never) : never }[keyof R & keyof Caps<T>]
  | (R extends { own: true; readableWhenUnloaded: true } ? 'require.own and require.readableWhenUnloaded are mutually exclusive' : never);
```

`own` and `readableWhenUnloaded` are exclusive by construction — bytes held *by* a target need the
target loaded, and bytes that are readable without it are by definition somewhere else.

**What stays a runtime refusal:** everything only the instance knows. A `Block` is `own` when its
type declares `minecraft:block_entity` and `proxied` when it does not; a `ContainerSlot` is `own`
only while its item is non-stackable (`maxAmount === 1` — a stackable item throws on write, live
slot included, [S5](./spikes/S5-abi-survey.md)). No type can see either, so `require: { own: true }`
on such a collection compiles, and `store.where(vanillaStone)` or `store.where(slotOfCobble)` comes
back `{ ok: false, reason: … }`. Likewise `own` plus `enumerable` on a block: satisfiable in the
type, impossible in fact, refused with a reason (the component ABI cannot list keys).

## Non-goals

- Queries, indexes, transactions. `for(id)` is the only lookup. Anything else is the addon's map.
- A "storage addon". The owner holds its data. There is no realm every other realm depends on.
- Replacing scoreboards for anything that must be readable from commands or JSON UI. Different tool.
